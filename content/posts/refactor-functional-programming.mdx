React Compiler의 동작 원리를 정리하면서, 컴파일러가 코드를 분석하는 방식 자체에 함수형 프로그래밍의 핵심 원칙이 녹아 있다는 걸 알게 됐습니다. SSA는 변수를 한 번만 할당하고, Effect 분석은 순수성을 판단하고, Reactive 분석은 파생 가능한 값을 찾아냅니다. 이 관점을 AI에게 주고 기존 코드를 분석하게 한 뒤, 그 결과를 바탕으로 리팩토링했더니 단순히 "함수형으로 바꿔줘"라고 한 것보다 훨씬 나은 결과가 나왔습니다.

## 컴파일러의 분석이 보여주는 것

React Compiler는 소스 코드를 최적화하기 위해 여러 단계의 정적 분석을 수행합니다. 이 분석 단계 각각이 함수형 프로그래밍의 원칙과 직접적으로 대응됩니다.

| 컴파일러 분석 | 핵심 동작 | 대응하는 함수형 원칙 |
|:--|:--|:--|
| SSA 변환 | 모든 변수를 한 번만 할당 | 불변 바인딩 (`const`) |
| Effect 분석 | Read/Mutate/Freeze 분류 | 순수 함수, 부수효과 격리 |
| Reactive 분석 | 파생 가능한 값 식별 | 상태 최소화, 계산된 값 |
| Scope 생성 | 독립적 캐싱 단위 분리 | 관심사 분리 |

SSA에서 `let label`이 `label_0`, `label_1`, `label_2 = φ(label_0, label_1)`로 변환되는 건, 변수의 재할당이 곧 새로운 값의 생성이라는 걸 구조적으로 보여줍니다. Effect 분석에서 Mutate로 분류된 연산이 scope를 확장시키는 건, 변이가 최적화를 어렵게 만든다는 걸 증명합니다. Reactive 분석에서 `formatName('Users')`가 non-reactive로 분류되는 건, 상수로부터 파생된 값은 상태로 관리할 필요가 없다는 뜻입니다.

컴파일러가 최적화하기 좋은 코드의 조건이 곧 함수형 코드의 특성입니다.

## AI에게 컴파일러 관점으로 분석시키기

"이 코드를 함수형으로 리팩토링해줘"라고 하면 AI는 일반적인 패턴 변환을 합니다. `for`를 `map`으로, `let`을 `const`로, 클래스를 함수로. 표면적인 변환은 되지만 어떤 변수가 왜 문제인지, 어떤 상태가 불필요한지에 대한 근거가 부족합니다.

대신 컴파일러의 분석 관점을 프롬프트로 주면 달라집니다.

```
다음 코드를 아래 기준으로 분석해줘:

1. SSA 관점: 재할당되는 변수를 찾고, 각 할당이 실제로 새로운 값인지 확인
2. Effect 관점: 각 연산을 Read/Store/Mutate/Freeze로 분류
3. Reactive 관점: props/state에서 파생 가능한 값과 독립적인 상수를 구분
4. Scope 관점: 같은 의존성을 공유하는 연산 그룹을 식별
```

이렇게 분석하면 코드의 구조적 문제가 구체적으로 드러납니다.

## 분석 기반 리팩토링 예시

실제 코드에 이 방식을 적용한 예시입니다.

```typescript
// 리팩토링 전
function OrderSummary({ items, coupon, user }) {
  let total = 0;
  let discountedTotal = 0;
  let displayItems = [];

  for (let i = 0; i < items.length; i++) {
    const item = items[i];
    if (item.inStock) {
      total += item.price * item.quantity;
      displayItems.push({
        ...item,
        subtotal: item.price * item.quantity,
      });
    }
  }

  if (coupon && coupon.isValid) {
    discountedTotal = total * (1 - coupon.discount);
  } else {
    discountedTotal = total;
  }

  const isVip = user.purchaseCount > 10;
  const vipLabel = isVip ? 'VIP' : 'Standard';
  const greeting = `${user.name}님 (${vipLabel})`;

  return (
    <div>
      <h1>{greeting}</h1>
      <ItemList items={displayItems} />
      <span>{discountedTotal}원</span>
    </div>
  );
}
```

AI에게 컴파일러 관점으로 분석을 요청하면 이런 결과가 나옵니다.

```
SSA 분석:
- total: 3곳에서 재할당 (0 → += → +=...) → 루프 내 누적
- discountedTotal: 2곳에서 할당 (if/else 분기) → φ 함수 대상
- displayItems: push로 반복 변이 → Mutate

Effect 분석:
- items.filter, price * quantity: Read (안전)
- displayItems.push: Mutate (scope 확장 필요)
- total +=: Mutate (누적 변이)

Reactive 분석:
- total, discountedTotal, displayItems: items + coupon에 의존 (reactive)
- greeting, vipLabel, isVip: user에만 의존 (reactive, 별도 scope)
- 'VIP', 'Standard' 문자열: non-reactive (상수)

Scope 분석:
- scope 1: items → displayItems, total → discountedTotal (items, coupon 의존)
- scope 2: user → isVip → vipLabel → greeting (user 의존)
- 두 scope는 독립적
```

이 분석을 바탕으로 리팩토링하면 각 변환의 근거가 명확합니다.

```typescript
// 리팩토링 후
function OrderSummary({ items, coupon, user }) {
  // scope 1: items, coupon에 의존
  const inStockItems = items.filter((item) => item.inStock);

  const displayItems = inStockItems.map((item) => ({
    ...item,
    subtotal: item.price * item.quantity,
  }));

  const total = inStockItems.reduce(
    (sum, item) => sum + item.price * item.quantity,
    0
  );

  const discountedTotal =
    coupon?.isValid ? total * (1 - coupon.discount) : total;

  // scope 2: user에 의존
  const vipLabel = user.purchaseCount > 10 ? 'VIP' : 'Standard';
  const greeting = `${user.name}님 (${vipLabel})`;

  return (
    <div>
      <h1>{greeting}</h1>
      <ItemList items={displayItems} />
      <span>{discountedTotal}원</span>
    </div>
  );
}
```

달라진 점을 정리하면 이렇습니다.

| 항목 | 변경 전 | 변경 후 | 근거 |
|:--|:--|:--|:--|
| `total` | `let` + `+=` 반복 | `reduce` 단일 표현식 | SSA: 재할당 제거 |
| `displayItems` | `push`로 변이 | `map`으로 새 배열 생성 | Effect: Mutate → Read |
| `discountedTotal` | `if/else` 분기 할당 | 삼항 연산자 | SSA: φ 함수 → 단일 할당 |
| `isVip` | 중간 변수 | 인라인 | Reactive: 불필요한 바인딩 제거 |
| scope 분리 | 코드가 섞여 있음 | 주석으로 scope 경계 표시 | Scope: 의존성 기준 그룹화 |

`let`이 전부 사라졌고, 변이 연산이 없어졌고, 각 값이 선언과 동시에 확정됩니다.

## 단순 요청 vs 분석 기반 요청

같은 코드에 대해 두 가지 방식으로 AI에게 리팩토링을 요청하면 결과가 다릅니다.

**단순 요청**: "이 코드를 함수형으로 리팩토링해줘"

AI는 `for`를 `forEach`나 `map`으로 바꾸고, `let`을 `const`로 바꾸는 수준에서 멈추는 경우가 많습니다. `total`을 `reduce`로 바꿔도 `displayItems`의 `push`는 그대로 두거나, 변환은 하되 scope 분리까지는 가지 않습니다. 왜 바꿔야 하는지에 대한 분석 없이 패턴만 대입하기 때문입니다.

**분석 기반 요청**: "SSA, Effect, Reactive, Scope 관점으로 분석한 뒤 리팩토링해줘"

분석 단계에서 각 변수의 재할당 횟수, 변이 여부, 의존성 그래프가 먼저 나옵니다. 이 분석이 리팩토링의 근거가 되므로 변환이 일관되고 빠뜨리는 부분이 적습니다. scope 분리까지 자연스럽게 이어지고, 결과 코드가 React Compiler의 최적화에도 유리한 형태가 됩니다.

```
분석 기반 접근:

코드 → AI가 컴파일러 관점으로 분석 → 문제 지점 도출 → 근거 기반 리팩토링

단순 접근:

코드 → AI가 패턴 매칭으로 변환 → 표면적 변경
```

차이의 핵심은 **분석이 먼저 이루어지는가**입니다. 컴파일러가 최적화 전에 HIR, SSA, Effect 분석을 수행하듯이, 리팩토링 전에 코드의 구조적 특성을 파악하면 변환의 방향과 근거가 생깁니다.

## 실무 적용 시 주의할 점

이 방식이 모든 리팩토링에 필요한 건 아닙니다. 간단한 유틸 함수나 이미 순수한 코드에 이 분석을 적용하는 건 과합니다. 효과가 큰 경우는 다음과 같습니다.

- **상태 변이가 섞인 렌더링 로직**: `let` + 재할당 + `push` 패턴이 반복되는 컴포넌트
- **여러 props에서 파생되는 계산**: 의존성 그래프가 복잡해서 scope 분리가 필요한 경우
- **성능 최적화가 필요한 컴포넌트**: React Compiler가 최적화하기 좋은 형태로 만들고 싶을 때

분석 결과를 맹신하지 말고 검증하는 것도 중요합니다. AI가 Read로 분류한 연산이 실제로는 내부에서 변이를 일으키는 경우도 있고, non-reactive로 판단한 값이 실제로는 외부 상태에 의존하는 경우도 있습니다.

## 정리

React Compiler의 분석 파이프라인은 최적화 도구이기도 하지만, 좋은 코드의 구조를 정의하는 기준이기도 합니다. SSA는 불변 바인딩을, Effect 분석은 순수 함수를, Reactive 분석은 상태 최소화를, Scope 생성은 관심사 분리를 지향합니다. AI에게 이 관점으로 코드를 먼저 분석하게 하고 그 결과를 바탕으로 리팩토링하면, 단순한 패턴 변환을 넘어서 구조적으로 개선된 코드를 얻을 수 있습니다.
