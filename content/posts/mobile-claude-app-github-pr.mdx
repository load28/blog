## 들어가며

출퇴근길에 문득 "아, 그 README에 설치 방법 빠졌지"가 떠오릅니다. 예전이라면 메모장에 적어뒀다가 노트북 앞에 앉아서야 처리했습니다. 지금은 폰을 꺼내서 Claude 앱을 열고, 저장소를 고르고, 한 줄 지시하면 끝입니다. 잠시 뒤 브랜치가 올라가 있고, diff를 확인한 뒤 **Create PR**을 누르면 PR이 열립니다.

이게 가능한 이유는 명확합니다. 코드가 **내 폰에서 도는 게 아니기 때문**입니다. Claude Code는 Anthropic이 관리하는 클라우드 VM에 저장소를 clone하고, 거기서 파일을 고치고 테스트를 돌린 뒤 브랜치를 push합니다. 폰은 그저 그 세션을 들여다보고 지시를 넣는 **원격 조종기**입니다. 그래서 로컬 개발 환경이 전혀 필요 없습니다.

이 글에서는 GitHub App을 설치해 연동을 붙이는 것부터, 모바일에서 PR을 만들고 그 뒤를 관리하는 것까지 순서대로 다룹니다.

## 0. 전체 그림부터

먼저 작업 하나가 어떤 경로를 타는지 알아두면 뒤의 설정이 왜 필요한지가 이해됩니다.

```text
[폰: Claude 앱 Code 탭]
        │  "README에 설치 방법 추가해줘"
        ▼
[Anthropic 관리 클라우드 VM]
        │  1. 저장소 clone (연결된 GitHub 계정 권한으로)
        │  2. 세팅 스크립트 실행 (설정한 경우)
        │  3. 네트워크 접근 레벨 적용
        │  4. 코드 수정 · 테스트 · 자체 검증
        │  5. 브랜치 push
        ▼
[GitHub]
        │  diff 확인 → Create PR
        ▼
[PR 생성 · 이후 CI/리뷰 대응]
```

여기서 중요한 지점이 두 개입니다.

- **브랜치 push까지가 기본 동작**입니다. PR 생성은 그다음에 내가 버튼을 눌러 하는 별도 단계입니다. Claude가 마음대로 PR을 열지 않습니다.
- **PR을 만든 뒤에도 세션은 계속 살아 있습니다.** CI가 깨지면 그 대화창에 그대로 이어서 고치라고 시키면 됩니다.

## 1. 준비물

| 항목 | 조건 |
|:--|:--|
| 플랜 | Pro, Max, Team. Enterprise는 premium seat 또는 Chat + Claude Code seat |
| GitHub | 작업할 저장소에 접근 가능한 GitHub 계정 |
| 앱 | iOS / Android Claude 앱 (또는 브라우저에서 claude.ai/code) |
| 저장소 | **이미 존재하는 GitHub 저장소**. 새 프로젝트라면 GitHub에서 빈 저장소를 먼저 만들어야 합니다 |

Claude Code on the web은 현재 리서치 프리뷰 단계입니다. 조직 계정이라면 Owner가 기능을 켜줘야 하는 경우가 있습니다.

## 2. GitHub 연동: 두 가지 방법

연동 방식은 두 가지고, **둘 중 아무거나 하나만 하면 됩니다.**

| 방법 | 동작 | 이럴 때 |
|:--|:--|:--|
| **GitHub App 설치** | 브라우저 온보딩에서 Claude GitHub App을 인가 | 폰/브라우저만으로 시작할 때, 그리고 Auto-fix를 쓸 때 |
| **`/web-setup`** | 터미널에서 로컬 `gh` CLI 토큰을 Claude 계정에 동기화 | 이미 `gh`를 쓰고 있는 개발자 |

이 글의 주제는 "폰으로 시작하기"이므로 GitHub App 쪽을 기준으로 설명합니다. 다만 **Auto-fix(PR 자동 대응)를 쓰려면 GitHub App 설치가 필수**입니다. `/web-setup`으로만 연결했다면 나중에라도 App을 설치해야 합니다.

### GitHub App 설치 절차

1. 브라우저에서 [claude.ai/code](https://claude.ai/code)에 접속해 Anthropic 계정으로 로그인합니다.
2. GitHub 연결 프롬프트가 뜹니다. 따라가면 Claude GitHub App 설치 화면으로 넘어갑니다.
3. 설치 대상 계정(개인 계정 또는 조직)을 고릅니다.
4. **Repository access**에서 접근 범위를 정합니다. `All repositories`와 `Only select repositories` 중에 고를 수 있습니다.
5. 설치를 완료하면 claude.ai/code로 돌아옵니다.

온보딩을 이미 지나쳤다면 [github.com/apps/claude](https://github.com/apps/claude)에서 직접 설치할 수도 있습니다.

조직 저장소인데 본인이 Owner가 아니라면, GitHub이 조직 관리자에게 **설치 승인 요청**을 보냅니다. 승인이 나기 전까지는 그 조직 저장소가 목록에 뜨지 않습니다.

### 여기서 오해하기 쉬운 것: App 설치 범위 ≠ 세션 접근 제어

이 부분은 반드시 짚고 넘어가야 합니다.

> 클라우드 세션은 **연결된 GitHub 계정이 볼 수 있는 모든 저장소**에 접근할 수 있습니다. GitHub App을 설치한 저장소로 한정되지 않습니다.

즉 `Only select repositories`로 딱 하나만 골라 설치했더라도, 세션 자체는 그 계정 권한이 닿는 다른 저장소도 clone할 수 있습니다. App 설치가 하는 일은 **PR 웹훅을 받는 것**(= Auto-fix 활성화)이지, 세션 단위의 접근 통제가 아닙니다.

팀에서 접근 범위를 실제로 제한하고 싶다면 GitHub 쪽에서 통제해야 합니다. 연결된 GitHub 계정의 팀 멤버십이나 저장소 멤버십을 조정하는 방식입니다. "App을 하나만 설치했으니 안전하다"는 잘못된 전제입니다.

### 터미널 파가 편하다면

`gh`를 이미 쓰고 있다면 브라우저를 안 열고 끝낼 수 있습니다.

```bash
# 1) gh 인증 (이미 되어 있으면 생략)
gh auth login
```

```text
# 2) Claude Code CLI 안에서 claude.ai 계정으로 로그인
/login

# 3) gh 토큰을 Claude 계정에 동기화
/web-setup
```

성공하면 `Connected as <github-username>`이 출력되고 브라우저로 claude.ai/code가 열립니다. 클라우드 환경이 없으면 이때 자동으로 하나 만들어 줍니다.

주의할 점 몇 가지입니다. `/web-setup`은 셸이 아니라 **Claude Code CLI 안에서** 입력해야 합니다. API 키로 인증한 상태에서는 명령 자체가 숨겨져 안 보입니다(`/login`으로 claude.ai 계정 로그인 필요). Team/Enterprise는 관리자가 "Quick web setup" 토글을 꺼두면 역시 안 보이고, Zero Data Retention이 켜진 조직은 클라우드 세션 기능 자체를 못 씁니다.

## 3. Default 환경 확인

GitHub 연결을 마치면 **Default**라는 이름의 클라우드 환경이 자동으로 만들어집니다. 환경은 세션의 네트워크 접근 범위, 환경변수, 세션 시작 시 실행할 세팅 스크립트를 담는 설정 묶음입니다.

Default는 **Trusted** 네트워크 접근을 씁니다. npm, PyPI 같은 일반적인 패키지 레지스트리와 허용 목록에 있는 도메인만 열려 있고 나머지는 막힙니다. 첫 프로젝트는 손댈 것 없이 그대로 쓰면 됩니다.

`pnpm install`이 사내 레지스트리를 봐야 한다든지, 세션 시작 전에 마이그레이션을 돌려야 한다든지 하는 요구가 생기면 그때 환경을 편집하거나 새로 만들면 됩니다. 이 환경 설정은 웹, 터미널, 모바일 앱 어디서 세션을 시작하든 똑같이 적용됩니다.

세팅 스크립트를 넣을 때는 **5분 정도의 시간 예산**을 염두에 둬야 합니다. 큰 Docker 이미지를 당겨오거나 의존성 트리를 통째로 동기화하는 무거운 단계를 직렬로 늘어놓으면 세션이 시작 단계에서 타임아웃 납니다. 독립적인 설치는 `&`와 `wait`로 병렬화하고, 정말 무거운 다운로드는 SessionStart 훅으로 빼서 백그라운드로 돌리는 편이 낫습니다.

## 4. 폰에서 작업 시작하기

여기부터가 본론입니다. 앱은 [iOS](https://apps.apple.com/us/app/claude-by-anthropic/id6473753684) / [Android](https://play.google.com/store/apps/details?id=com.anthropic.claude)에서 받습니다. 터미널에서 `/mobile`을 치면 QR 코드가 나옵니다.

### 저장소와 브랜치 선택

앱에서 **Code 탭**으로 들어갑니다. 입력창 아래 저장소 선택기를 누르면 접근 가능한 저장소 목록이 뜹니다.

- 저장소마다 **브랜치 선택기**가 따로 있습니다. 기본 브랜치가 아니라 특정 피처 브랜치에서 출발시키고 싶으면 여기서 바꿉니다.
- 저장소를 **여러 개 추가**해 한 세션에서 같이 다룰 수도 있습니다. 프론트/백엔드가 갈라져 있는 구조에서 유용합니다.

### 권한 모드 고르기

입력창 옆 모드 드롭다운은 기본값이 **Accept edits**입니다. 승인을 기다리지 않고 바로 고치고 브랜치를 push하는 모드입니다.

| 모드 | 동작 |
|:--|:--|
| Accept edits (기본) | 중간 승인 없이 수정 후 브랜치 push |
| Plan | 파일을 고치기 전에 접근 방법을 제안하고 내 승인을 기다림 |
| Auto | 상황에 따라 자동 판단 |

클라우드 세션에는 Manual과 Bypass가 없습니다.

여기서 실전 감각을 하나 덧붙이면 — **폰으로 지시할 때는 Plan 모드가 오히려 불편할 수 있습니다.** 승인 프롬프트에서 세션이 멈춰 서기 때문입니다. 폰을 주머니에 넣고 다른 일을 하다가 나중에 봤더니 첫 질문에서 멈춰 있는 상황이 생깁니다. 범위가 명확한 작업이라면 Accept edits로 던져놓고 결과 diff를 보고 판단하는 쪽이 모바일 흐름에 맞습니다.

### 작업 지시 쓰기

여기가 결과 품질을 가장 크게 가르는 지점입니다. 폰이라 타이핑이 귀찮다고 "테스트 고쳐줘"라고 보내면 엉뚱한 걸 고쳐옵니다.

```text
❌ "테스트 고쳐줘"

✅ "tests/test_auth.py의 실패하는 인증 테스트를 고쳐줘.
    만료된 토큰에서 401을 기대하는데 500이 나오고 있어.
    로그: TypeError: 'NoneType' object is not subscriptable at auth.py:83"
```

세 가지만 지키면 됩니다.

1. **파일이나 함수 이름을 지목**합니다. 클라우드 세션은 내 로컬 컨텍스트를 모릅니다.
2. **에러 출력을 그대로 붙여넣습니다.** 폰에서도 복붙은 됩니다.
3. **증상이 아니라 기대 동작을 씁니다.** "안 돼요"가 아니라 "이렇게 되어야 하는데 이렇게 됩니다".

저장소에 `CLAUDE.md`를 커밋해두면 매 세션 시작 시 자동으로 읽힙니다. 컨벤션이나 프로젝트 구조 설명을 거기 넣어두면, 폰에서 짧게 지시해도 결과가 훨씬 안정적입니다. 모바일 작업을 진지하게 할 생각이라면 이 투자가 가장 수익률이 높습니다.

전송하면 각 작업이 **자기만의 세션과 자기만의 브랜치**를 갖습니다. 하나가 끝날 때까지 기다릴 필요 없이 다음 작업을 바로 던져도 됩니다.

### 앱을 닫아도 됩니다

세션은 클라우드에서 돌기 때문에 앱을 닫거나 화면을 꺼도 계속 진행됩니다. 나중에 다시 열면 그 자리에 있습니다. 노트북에서 시작한 세션을 폰에서 이어보는 것도 됩니다.

## 5. diff 리뷰하고 PR 만들기

작업이 끝나면 `+42 -18` 같은 diff 인디케이터가 뜹니다. 이걸 누르면 diff 뷰가 열립니다.

### 인라인 코멘트로 피드백 주기

diff에서 특정 줄을 선택하고 피드백을 타이핑한 뒤 엔터를 누르면 코멘트가 쌓입니다. 이 코멘트들은 **다음 메시지를 보낼 때 함께 묶여서** 전달됩니다.

이게 폰에서 특히 좋습니다. "src/auth.ts 47번 줄에서 에러를 catch하지 말고 위로 올려줘"라고 위치를 말로 설명할 필요 없이, 그 줄을 짚고 "여기서 catch하지 마"라고만 쓰면 됩니다. 작은 화면에서 긴 설명을 타이핑하는 부담이 크게 줄어듭니다.

### Create PR

diff가 마음에 들면 diff 뷰 상단의 **Create PR**을 누릅니다. 세 가지 선택지가 있습니다.

| 선택지 | 결과 |
|:--|:--|
| 정식 PR | 바로 열림 |
| Draft PR | 초안 상태로 열림. 리뷰 요청 전 CI만 먼저 돌려보고 싶을 때 |
| GitHub compose 페이지로 이동 | 제목·본문이 생성된 상태로 GitHub 작성 화면이 열림. 라벨·리뷰어·템플릿을 직접 손볼 때 |

폰에서는 개인적으로 **Draft**를 기본값처럼 씁니다. 일단 열어서 CI를 돌려놓고, 초록불이 뜬 걸 확인한 뒤 Ready for review로 전환하는 흐름이 이동 중에 가장 편합니다.

PR을 만든 뒤에도 **세션은 그대로 살아 있습니다.** CI 실패 로그나 리뷰어 코멘트를 붙여넣고 "이거 처리해줘"라고 하면 같은 브랜치에 이어서 커밋합니다.

## 6. PR 이후: Auto-fix

매번 로그를 붙여넣는 게 번거롭다면 **Auto-fix**를 켭니다. Claude가 해당 PR의 GitHub 활동을 구독해서, CI가 깨지거나 리뷰 코멘트가 달리면 알아서 조사하고 명확한 수정은 바로 push합니다.

> Auto-fix는 **Claude GitHub App이 해당 저장소에 설치되어 있어야** 동작합니다. 웹훅을 App으로 받기 때문입니다. `/web-setup`으로만 연결했다면 여기서 App 설치가 필요해집니다.

켜는 방법은 상황별로 다릅니다.

- **웹에서 만든 PR**: CI 상태 바를 열고 **Auto-fix** 선택
- **모바일 앱**: 그냥 말로 시킵니다. "이 PR 지켜보다가 CI 실패나 리뷰 코멘트 생기면 고쳐줘"
- **터미널**: PR 브랜치에서 `/autofix-pr`
- **아무 기존 PR**: 세션에 PR URL을 붙여넣고 auto-fix 해달라고 요청

동작 방식은 이벤트마다 판단이 갈립니다. 확신이 있고 기존 지시와 충돌하지 않는 수정은 바로 push하고 세션에 설명을 남깁니다. 해석이 갈리거나 구조적으로 중요한 변경은 나에게 먼저 물어봅니다. 중복이거나 조치가 불필요한 이벤트는 기록만 남기고 넘어갑니다.

### Auto-fix의 한계와 위험

두 가지는 알고 켜야 합니다.

**충돌은 자동으로 못 잡습니다.** base 브랜치가 앞서 나가서 머지 충돌이 생겨도 GitHub이 웹훅을 쏘지 않기 때문에, Auto-fix가 스스로 반응할 수 없습니다. 세션을 열어서 리베이스를 직접 시켜야 합니다.

**Claude의 답글이 내 계정으로 나갑니다.** 리뷰 코멘트 스레드에 다는 답글은 내 GitHub 계정으로 게시됩니다(Claude Code가 쓴 것이라는 라벨은 붙습니다). 그래서 `issue_comment` 이벤트로 도는 자동화 — Atlantis, Terraform Cloud, 커스텀 GitHub Actions 같은 것 — 가 걸려 있는 저장소라면 조심해야 합니다. PR 코멘트 하나가 인프라를 배포할 수 있는 저장소에서는 Auto-fix를 끄는 게 맞습니다.

끄는 건 CI 상태 바의 토글을 해제하거나, 그냥 "이 PR 그만 봐도 돼"라고 말하면 됩니다. PR 단위 토글입니다.

## 7. 알아두면 좋은 것들

### URL로 세션 미리 채우기

claude.ai/code에 쿼리 파라미터를 붙이면 프롬프트와 저장소가 미리 선택된 상태로 열립니다.

```text
https://claude.ai/code?prompt=Fix%20the%20login%20bug&repositories=acme/webapp
```

| 파라미터 | 설명 |
|:--|:--|
| `prompt` | 입력창에 채울 텍스트 (`q`도 가능) |
| `prompt_url` | 프롬프트가 길 때 가져올 URL. CORS 허용 필요 |
| `repositories` | `owner/repo` 콤마 구분 목록 (`repo`도 가능) |
| `environment` | 사용할 환경 이름 또는 ID |

이슈 트래커에 "Claude로 열기" 버튼을 다는 식으로 쓸 수 있습니다. 이슈 본문을 프롬프트로 넘기면, 폰에서 이슈를 보다가 버튼 하나로 작업을 시작할 수 있습니다.

### 폰에서 시작해서 노트북에서 이어받기

이동 중에 폰으로 던져놓은 작업을 집에 와서 터미널에서 이어받고 싶다면 `--teleport`를 씁니다.

```bash
claude --teleport            # 세션 선택기
claude --teleport <session-id>   # 특정 세션 바로 이어받기
```

해당 저장소 체크아웃에서 실행해야 하고, 워킹 디렉토리가 깨끗해야 하며(더러우면 stash하라고 물어봅니다), 같은 claude.ai 계정이어야 합니다. 세션의 브랜치를 fetch·checkout하고 대화 히스토리 전체를 터미널로 가져옵니다.

단, 텔레포트 이후의 작업은 **로컬에만 남습니다.** 클라우드 세션 쪽에는 반영되지 않으므로 폰에서 계속 지켜볼 수 없게 됩니다. 텔레포트 후에도 폰에서 조종하고 싶다면 로컬 세션에서 `/remote-control`을 켜야 합니다.

### 병렬로 던지기

작업마다 세션과 브랜치가 분리되므로, 서로 독립적인 일은 그냥 여러 개 던져두면 됩니다. 워크트리를 여러 개 관리할 필요가 없다는 게 이 방식의 큰 장점입니다. 다만 병렬 실행은 그만큼 rate limit을 더 씁니다.

## 8. 한계

기대치를 맞춰두는 게 좋습니다.

| 항목 | 내용 |
|:--|:--|
| Rate limit | 계정의 다른 Claude 사용량과 **공유**합니다. 병렬 실행은 비례해서 더 소모합니다. VM 자체에 별도 과금은 없습니다 |
| GitHub 필수 | clone과 PR 생성은 GitHub이 있어야 합니다. GitLab·Bitbucket은 로컬 번들로 보낼 수는 있지만 결과를 push해 되돌릴 수 없습니다 |
| 로컬 설정 | 클라우드 세션은 내 로컬 설정을 쓰지 않습니다. 저장소 안의 것만 봅니다 |
| IP allowlist | 조직에 IP 허용 목록이 걸려 있으면 Anthropic 호스팅 세션은 인증 에러로 전부 실패합니다. 지원팀에 예외 등록을 요청해야 합니다 |
| ZDR | Zero Data Retention이 켜진 조직은 클라우드 세션 기능을 쓸 수 없습니다 |
| 세션 만료 | 일정 시간 유휴하면 VM이 회수됩니다. 다시 열면 대화 히스토리는 복원된 채로 새 VM이 뜹니다 |

그리고 무엇보다 — **자주 개입해야 하는 작업에는 안 맞습니다.** 폰으로 하는 작업은 "잘 정의된 일을 던져놓고 나중에 결과를 본다"는 흐름일 때 가장 잘 굴러갑니다. 5분마다 방향을 틀어줘야 하는 탐색적인 작업이라면 노트북 앞에 앉는 게 맞습니다.

## 마무리

정리하면 세 단계입니다.

1. **한 번만**: claude.ai/code에서 GitHub App 설치 → Default 환경 확인
2. **매번**: 앱 Code 탭 → 저장소·브랜치 선택 → 구체적으로 지시
3. **결과**: diff 확인 → 인라인 코멘트로 다듬기 → Create PR → 필요하면 Auto-fix

이 흐름이 바꾸는 건 "코딩을 폰으로 한다"가 아닙니다. **작업을 시작하는 비용을 거의 0으로 만드는 것**입니다. 노트북을 열고, 브랜치를 파고, 컨텍스트를 다시 복원하는 그 마찰 때문에 미뤄뒀던 작은 일들 — README 보강, 오타 수정, 플래키 테스트 하나 — 이 떠오른 그 자리에서 처리됩니다.

설정할 때 하나만 기억하면 됩니다. **App 설치 범위는 접근 제어가 아닙니다.** 실제 통제는 GitHub 계정의 저장소 권한으로 해야 합니다.
