## 로딩 플리커 문제

API 응답이 빠르면 로딩 UI가 아주 잠깐 보였다가 사라집니다. 스피너든 스켈레톤이든 "로딩 상태 → 완료 상태" 전환이 너무 빠르면 시각적 노이즈가 됩니다.
이건 UI 패턴의 문제가 아니라 **상태 전환 타이밍의 문제**입니다.

Nielsen Norman Group에 따르면 1초 미만으로 로드되는 작업에 루프 애니메이션(스피너)을 사용하는 것은 오히려 방해가 됩니다.
화면에 무언가 번쩍였다는 사실 자체가 사용자를 불안하게 만들기 때문입니다. 스피너는 2~10초 사이의 작업에 적합합니다.

## 실무에서 사용하는 로딩 패턴

### Delayed Spinner

가장 간단하고 직접적인 해결책입니다. `spin-delay` 라이브러리가 이 패턴을 공식화했습니다.

```typescript
const showSpinner = useSpinDelay(loading, {
  delay: 500,     // 500ms 이후에만 스피너 표시
  minDuration: 200 // 표시되면 최소 200ms 유지
});
```

네트워크 요청이 빠르면 스피너를 아예 보여주지 않고, 스피너가 표시된 경우엔 최소 시간을 유지해서 플리커를 방지합니다.
TanStack Query 메인테이너도 "최소 로딩 시간을 늘리는 것보다, 약 250ms 이후에 스피너를 표시하는 방식으로 접근하라"고 권고합니다.
앱을 필요 이상으로 느리게 만들지 말라는 것이 핵심입니다.

### Skeleton Screen

Material UI, GitHub, LinkedIn, YouTube 등이 사용하는 방식입니다.
스피너 대신 콘텐츠의 자리를 미리 채워서 즉시 무언가 일어나는 것처럼 느끼게 합니다.
다만 스켈레톤도 API가 빠르면 똑같이 번쩍이는 문제가 생깁니다. 결국 `spin-delay`와 조합해야 합니다.

```typescript
const showSkeleton = useSpinDelay(isLoading, {
  delay: 300,
  minDuration: 500
});

return showSkeleton ? <Skeleton /> : <Content />;
```

| 상황 | 권장 패턴 |
|:--|:--|
| 페이지 초기 데이터 로딩 | Skeleton + delay |
| 버튼 클릭 → 목록 갱신 | Delayed Spinner (delay: 300~500ms) |
| 파일 업로드 등 긴 작업 | Determinate Progress Bar |

## 로딩을 없애는 전략: 캐시

"로딩을 어떻게 보여줄까"보다 먼저 고민해야 할 질문은 **"로딩을 아예 안 보여줄 수 있는가"** 입니다.

### Stale-While-Revalidate

TanStack Query의 핵심 동작입니다. 같은 query key로 두 번째 마운트가 발생하면 캐시에 있는 데이터를 즉시 반환하고, 동시에 백그라운드에서 새 네트워크 요청을 보냅니다.

```
첫 방문:     [로딩] → [데이터 표시]
두 번째 방문: [이전 데이터 즉시 표시] → (백그라운드 갱신) → [새 데이터로 교체]
```

Gmail, Notion, Linear 등이 빠르게 느껴지는 이유입니다.

### staleTime과 gcTime의 역할

많은 개발자들이 `staleTime`을 "캐시 유지 시간"으로 오해합니다. 실제로는 역할이 완전히 다릅니다.

| 옵션 | 역할 | 영향 |
|:--|:--|:--|
| `staleTime` | 백그라운드 리패치 트리거 시점 | 데이터 신선도 |
| `gcTime` | 캐시 메모리 삭제 시점 | 로딩 발생 여부 |

두 옵션은 각각 **UX 레이어**(로딩 발생 여부)와 **데이터 신선도 레이어**를 담당하는 독립적인 축입니다. 캐시가 메모리에 남아있는 한 로딩은 발생하지 않습니다. `staleTime`은 그 캐시로 백그라운드 리패치를 할지 말지를 결정할 뿐입니다.

```
gcTime: 10분, staleTime: 5분일 때

3분에 복귀  → 캐시 즉시 표시, 리패치 없음 (fresh)
6분에 복귀  → 캐시 즉시 표시 + 백그라운드 리패치 (stale)
11분에 복귀 → 캐시 없음 → 로딩 발생 (gc 완료)
```

### status와 fetchStatus 분리

TanStack Query는 `status`(데이터 유무)와 `fetchStatus`(요청 진행 여부)를 분리합니다. 이 두 가지를 구분해서 UI를 다르게 처리하는 것이 핵심입니다.

```typescript
const { data, status, fetchStatus } = useQuery(...)

// status === 'pending' && fetchStatus === 'fetching'
// → 진짜 첫 로딩 → 스켈레톤

// status === 'success' && fetchStatus === 'fetching'
// → 백그라운드 갱신 → 아무것도 안 보여줌

// status === 'success' && fetchStatus === 'idle'
// → 완료 → 데이터 표시
```

백그라운드 리패치는 사용자에게 알릴 필요가 없습니다. Gmail, Notion, Linear 같은 앱들도 백그라운드에서 조용히 갱신하고 새 데이터가 오면 자연스럽게 교체할 뿐, "지금 불러오는 중"이라는 표시를 하지 않습니다.
opacity 처리나 스피너를 표시하는 순간 캐시 전략의 UX적 이점이 사라집니다.

### 백그라운드 리패치의 UX 문제

다만 테이블처럼 사용자가 데이터를 읽고 있는 중에 백그라운드 리패치로 행이 갑자기 바뀌거나 순서가 변경되면 혼란을 줄 수 있습니다. 이 경우 두 가지 패턴이 있습니다.

- **상단 토스트/배너로 알림** — "새로운 데이터가 있습니다 → 새로고침" 버튼을 제공. 사용자가 원할 때 반영 (GitHub 이슈 목록 방식)
- **변경된 행만 하이라이트** — 바뀐 셀에 짧은 색상 애니메이션으로 어디가 바뀌었는지 맥락 제공

무조건 조용히 교체하는 것이 정답이 아니라, 데이터가 얼마나 자주 바뀌고 사용자가 그 데이터를 어떻게 소비하는가에 따라 전략이 달라집니다.

### staleTime은 쿼리별로 설정

앱 전체에 `staleTime`을 하나로 통일하는 것보다 데이터 성격별로 다르게 설정하는 것이 맞습니다.

```typescript
// 자주 안 바뀌는 데이터
useQuery({ queryKey: ['profile'], staleTime: Infinity, gcTime: 10 * 60 * 1000 })

// 자주 바뀌는 데이터
useQuery({ queryKey: ['feed'], staleTime: 0, gcTime: 5 * 60 * 1000 })
```

## 실시간 데이터 처리

### 내가 변경한 데이터: Optimistic Update

```typescript
useMutation({
  mutationFn: updateItem,
  onMutate: async (newItem) => {
    await queryClient.cancelQueries({ queryKey: ['items'] })
    const previous = queryClient.getQueryData(['items'])
    queryClient.setQueryData(['items'], (old) =>
      old.map(item => item.id === newItem.id ? newItem : item)
    )
    return { previous }
  },
  onError: (err, newItem, context) => {
    queryClient.setQueryData(['items'], context.previous)
  },
  onSettled: () => {
    queryClient.invalidateQueries({ queryKey: ['items'] })
  }
})
```

### 다른 사람이 변경한 데이터: 이벤트 기반 무효화

Jira는 과거에 1분마다 폴링을 했는데, 이를 이벤트 드리븐 아키텍처로 전환했습니다.
변경이 발생했을 때만 프론트엔드에 push하는 방식입니다.

```typescript
// 저빈도 변경 (협업 툴) — 이벤트로 캐시 무효화
socket.on('dataChanged', ({ queryKey }) => {
  queryClient.invalidateQueries({ queryKey })
})

// 고빈도 변경 (주식, 실시간 지표) — 데이터 직접 주입
socket.on('priceUpdated', (updated) => {
  queryClient.setQueryData(['stock', updated.ticker], updated)
})
```

저빈도 변경은 `invalidateQueries`로 리패치를 트리거하고, 고빈도 변경은 `setQueryData`로 네트워크 요청 없이 캐시를 직접 덮어씁니다.
`invalidateQueries`는 "서버에 다시 물어봐라", `setQueryData`는 "이 값으로 캐시를 덮어써라"의 차이입니다.

소켓을 쓰면 `staleTime`이 길어도 문제없습니다. 데이터가 바뀌는 시점을 이미 알고 있기 때문에 그때 명시적으로 캐시를 깨거나 업데이트하면 됩니다.
"항상 최신"이 아니라 **"변경됐을 때만 갱신"** 이 더 정확한 전략입니다.

### 전역 소켓 vs 페이지 소켓

소켓 연결이 페이지 레벨에서만 일어나면, 페이지를 떠나는 순간 소켓도 끊깁니다. 돌아왔을 때 캐시가 있어도 그 사이 변경된 데이터는 반영이 안 됩니다.

이를 해결하려면 소켓을 앱 최상단에서 전역으로 유지하고 `setQueryData`로 계속 갱신해야 합니다. 페이지를 떠나도 소켓은 살아있으니 캐시가 항상 최신 상태를 유지합니다. 이때 `gcTime`은 소켓 연결 유지 시간 이상으로 충분히 길게 설정해야 합니다. `gcTime`이 짧으면 페이지를 떠나는 순간 캐시가 삭제되어 소켓이 `setQueryData`를 해도 저장할 캐시가 없습니다.

다만 모든 페이지 데이터를 전역 소켓으로 관리하는 복잡도가 부담된다면, 페이지 복귀 시 매번 리패치하되 `spin-delay`로 처리하는 것이 현실적인 대안입니다.

## SSR은 답이 아닌가

SSR로 서버에서 데이터를 미리 채워서 보내면 로딩을 없앨 수 있습니다. TanStack Query도 `dehydrate` / `HydrationBoundary`로 이를 공식 지원합니다.

하지만 엔터프라이즈에서 SSR을 선택하는 이유는 로딩 제거가 아니라 SEO, 초기 LCP 개선이 주된 이유입니다.
로딩 UX만을 위해 SSR 서버 부하를 감수하는 경우는 거의 없고, 캐시 전략 + Optimistic Update + WebSocket 조합으로 CSR에서 해결하는 것이 일반적입니다.

## 데이터 성격별 전략

결국 로딩을 어떻게 보여줄까가 아니라 **데이터 성격을 먼저 파악하는 것**이 핵심입니다.

| 데이터 변경 빈도 | 전략 | 결과 |
|:--|:--|:--|
| 거의 안 바뀜 (프로필, 설정) | `gcTime` + `staleTime` 길게 | 로딩 없음, 백그라운드 갱신 |
| 자주 바뀜 (피드, 목록) | 캐시 포기, 매번 리패치 | spin-delay로 자연스럽게 |
| 실시간 (협업 툴) | 소켓 이벤트 → `invalidateQueries` | 변경 시점에만 갱신 |
| 초고빈도 실시간 (주식) | 소켓 데이터 → `setQueryData` 직접 주입 | 로딩 자체가 없는 구조 |

자주 바뀌는 데이터는 `staleTime` 구간에 오래된 데이터를 볼 수 있고, 리패치 시 UI 전환 문제도 존재합니다.
이런 경우 캐시를 포기하고 매번 리패치하되, `spin-delay`로 처리하는 것이 현실적입니다.
대부분의 API가 300ms 이내에 응답한다면 사용자는 로딩 없이 바로 데이터를 보게 됩니다.

반대로 거의 바뀌지 않는 데이터까지 매번 리패치하면 불필요한 로딩이 발생합니다.
이런 데이터는 캐시 전략으로 로딩 자체를 없애는 것이 맞습니다.

**"로딩을 없앨 수 있는 곳은 캐시 전략으로 없애고, 없앨 수 없는 곳만 spin-delay로 자연스럽게 처리한다"** — 이것이 로딩 UX의 본질입니다.
