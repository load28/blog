Angular, Vue, Solid, Svelte, Preact — 프론트엔드 프레임워크마다 자체적인 반응형 시스템을 갖고 있습니다. 문제는, 이들이 서로 호환되지 않는다는 것입니다. 한 프레임워크에서 만든 반응형 라이브러리를 다른 프레임워크에서 쓸 수 없고, 같은 로직을 프레임워크마다 다시 만들어야 합니다.

TC39 Signals 제안은 이 반응형 시스템의 **공통 기반**을 JavaScript 언어 차원에서 표준화하려는 시도입니다. 현재 Stage 1 단계이며, Angular, Vue, Solid, Svelte, Preact, MobX, Ember, Qwik 등 주요 프레임워크 저자들이 함께 설계에 참여하고 있습니다.

## Signal이 뭔가요?

Signal은 **값을 감싸는 반응형 컨테이너**입니다. 일반 변수와 다른 점은, 값이 바뀌면 그 값에 의존하는 다른 코드가 자동으로 알 수 있다는 것입니다.

일반 JavaScript로 카운터를 만들면 이렇습니다.

```javascript
let counter = 0;

const setCounter = (value) => {
  counter = value;
  render(); // 값이 바뀔 때마다 수동으로 render를 호출해야 함
};

const isEven = () => (counter & 1) == 0;
const parity = () => isEven() ? "even" : "odd";
const render = () => element.innerText = parity();

setInterval(() => setCounter(counter + 1), 1000);
```

`counter`가 바뀌면 `render()`를 직접 호출해야 합니다. `isEven`이나 `parity`가 `counter`에 의존한다는 사실을 코드 어디에도 선언하지 않았기 때문입니다. 개발자가 이 의존 관계를 머릿속에 담아두고 수동으로 관리해야 합니다.

Signal을 쓰면 이렇게 바뀝니다.

```javascript
const counter = new Signal.State(0);
const isEven = new Signal.Computed(() => (counter.get() & 1) == 0);
const parity = new Signal.Computed(() => isEven.get() ? "even" : "odd");

effect(() => element.innerText = parity.get());

setInterval(() => counter.set(counter.get() + 1), 1000);
```

`counter`가 바뀌면 `isEven` → `parity` → `effect`까지 자동으로 전파됩니다. 의존 관계를 직접 선언할 필요도 없습니다. 런타임이 `get()` 호출을 추적해서 알아서 파악합니다.

## 핵심 API

표준 제안의 API는 크게 세 가지입니다.

### Signal.State — 변경 가능한 값

가장 기본적인 Signal입니다. 읽고 쓸 수 있는 반응형 값을 만듭니다.

```javascript
const name = new Signal.State("Alice");

name.get();       // "Alice"
name.set("Bob");  // 값 변경 → 의존하는 Computed들에 알림
name.get();       // "Bob"
```

### Signal.Computed — 파생된 값

다른 Signal들로부터 계산되는 **읽기 전용** 값입니다. 핵심 특징이 세 가지 있습니다.

```javascript
const firstName = new Signal.State("Min");
const lastName = new Signal.State("Seo");

const fullName = new Signal.Computed(() => {
  return firstName.get() + " " + lastName.get();
});

fullName.get(); // "Min Seo"
```

**1. 자동 의존성 추적 (Auto-tracking)**

`fullName`의 콜백 함수가 실행될 때, 런타임은 내부에서 호출된 모든 `get()`을 감지합니다. `firstName.get()`과 `lastName.get()`이 호출되었으므로, `fullName`은 자동으로 `firstName`과 `lastName`에 의존한다고 기록됩니다.

의존성 배열을 수동으로 관리하는 React의 `useMemo`와 비교해보면 차이가 명확합니다.

```javascript
// React — 의존성을 개발자가 직접 나열
const fullName = useMemo(
  () => firstName + " " + lastName,
  [firstName, lastName] // 빠뜨리면 버그
);

// Signals — 런타임이 자동으로 파악
const fullName = new Signal.Computed(
  () => firstName.get() + " " + lastName.get()
  // 의존성 배열 불필요
);
```

**2. 지연 평가 (Lazy Evaluation)**

Computed는 누군가 `get()`을 호출할 때만 계산됩니다. 아무도 읽지 않는 Computed는 의존하는 값이 아무리 바뀌어도 다시 계산되지 않습니다.

```javascript
const heavy = new Signal.Computed(() => {
  return expensiveCalculation(source.get());
});

// source가 100번 바뀌어도...
// heavy.get()을 호출하기 전까지 expensiveCalculation은 실행되지 않음
```

**3. 메모이제이션**

한번 계산된 값은 캐시됩니다. 의존하는 값이 바뀌지 않았다면, `get()`을 여러 번 호출해도 콜백을 다시 실행하지 않고 캐시된 값을 반환합니다.

### Signal.subtle.Watcher — 변경 감지기

`Signal.subtle` 네임스페이스는 `crypto.subtle`처럼, 주의해서 사용해야 하는 고급 API입니다. 일반 애플리케이션 코드가 아니라 프레임워크나 라이브러리 저자를 위한 도구입니다.

```javascript
const watcher = new Signal.subtle.Watcher(() => {
  // Signal이 dirty해지면 호출됨 (동기적)
  // 여기서는 Signal을 읽거나 쓸 수 없음 — 스케줄링만 가능
});

watcher.watch(parity);    // parity Signal 감시 시작
watcher.getPending();     // dirty 상태인 Signal 목록 반환
watcher.unwatch(parity);  // 감시 해제
```

중요한 제약이 있습니다. `notify` 콜백 안에서는 **Signal을 읽거나 쓸 수 없습니다.** 콜백은 `set()` 호출 도중에 동기적으로 실행되기 때문에, 이 시점에 Signal 그래프가 반만 업데이트된 상태일 수 있습니다. 콜백에서 할 수 있는 일은 "나중에 처리하겠다"고 스케줄링하는 것뿐입니다.

## 반응형 그래프와 Push-Pull 알고리즘

Signal들은 의존 관계에 따라 **방향성 비순환 그래프(DAG)**를 형성합니다. 이 그래프가 업데이트되는 방식이 Signals의 핵심입니다.

### 노드의 세 가지 상태

```
Clean  → 현재 값이 최신. 다시 계산할 필요 없음
Dirty  → 의존하는 소스가 변경됨. 반드시 다시 계산해야 함
Check  → 소스의 소스가 변경됨. 실제로 영향받는지 확인이 필요함
```

### Push 단계 — "더러워졌다고 알리기"

State Signal의 `set()`이 호출되면, 의존 그래프를 따라 아래로 **dirty 플래그를 전파**합니다.

```
counter.set(2)
    │
    ▼
  counter [Dirty]
    │
    ├──▶ isEven  [Dirty]   ← counter에 직접 의존
    │       │
    │       ▼
    │    parity  [Check]   ← isEven에 의존 (간접)
    │       │
    │       ▼
    │    watcher [Check]   ← parity에 의존 (간접)
    │
    ▼
  (Push 완료 — 아직 아무것도 계산하지 않음)
```

여기서 주목할 점은 `parity`와 `watcher`가 `Dirty`가 아니라 **`Check`** 상태라는 것입니다. `counter`가 바뀌었지만, `isEven`의 결과가 실제로 바뀌는지는 아직 모릅니다. 예를 들어 `counter`가 2에서 4로 바뀌면 `isEven`은 여전히 `true`이고, `parity`는 다시 계산할 필요가 없습니다.

이 단계에서는 **아무 계산도 하지 않습니다.** 단지 "확인이 필요하다"는 플래그만 전파합니다.

### Pull 단계 — "실제로 값이 필요할 때 계산하기"

누군가 `parity.get()`을 호출하면 Pull이 시작됩니다.

```
parity.get() 호출
    │
    ▼
  parity는 Check 상태 → 소스(isEven) 확인 필요
    │
    ▼
  isEven은 Dirty 상태 → 다시 계산
    │
    ▼
  isEven 콜백 실행: counter.get() & 1 == 0
    │
    ├─ 결과가 이전과 같음 → isEven을 Clean으로
    │   └─ parity도 Clean으로 (다시 계산 불필요!)
    │
    └─ 결과가 달라짐 → isEven을 Clean으로
        └─ parity를 Dirty로 승격 → 다시 계산
```

Pull 단계의 핵심은 **소스부터 순서대로 확인**한다는 것입니다. 위상 정렬(topological sort)을 통해 그래프의 상위 노드부터 평가하므로, 한 노드가 여러 번 계산되는 일이 없습니다.

### 왜 Push-Pull인가?

순수 Push 방식과 순수 Pull 방식 각각의 단점을 보완합니다.

| 방식 | 장점 | 단점 |
|:--|:--|:--|
| Push only | 변경 즉시 전파 | 불필요한 계산 발생 (아무도 안 읽는 값도 계산) |
| Pull only | 필요한 것만 계산 | 무엇이 바뀌었는지 모르므로 전체를 확인해야 함 |
| **Push-Pull** | 변경 알림은 즉시 + 계산은 필요할 때만 | — |

Push로 "어디가 바뀌었는지" 빠르게 표시하고, Pull로 "실제 값이 필요할 때만" 계산합니다.

## 다이아몬드 문제

반응형 시스템에서 가장 유명한 문제입니다. 하나의 소스에서 두 갈래로 갈라졌다가 다시 합쳐지는 의존 관계를 생각해봅시다.

```javascript
const a = new Signal.State(1);
const b = new Signal.Computed(() => a.get() * 2);  // a → b
const c = new Signal.Computed(() => a.get() * 3);  // a → c
const d = new Signal.Computed(() => b.get() + c.get());  // b, c → d
```

의존 그래프가 다이아몬드 형태입니다.

```
      a
     / \
    b   c
     \ /
      d
```

`a`가 1에서 2로 바뀌면, `d`는 `b`와 `c`가 모두 업데이트된 후에 한 번만 계산되어야 합니다. 만약 `b`만 업데이트된 시점에 `d`를 계산하면 `b`는 새 값(4), `c`는 옛날 값(3)을 사용하게 됩니다. 이런 **일시적 불일치 상태를 Glitch**라고 부릅니다.

```
잘못된 순서 (Glitch 발생):
  a = 2
  b = 4        ← a * 2 (새 값)
  d = 4 + 3    ← b(새) + c(옛) = 7  ❌ Glitch!
  c = 6        ← a * 3 (새 값)
  d = 4 + 6    ← b(새) + c(새) = 10 ✅

올바른 순서 (Glitch-free):
  a = 2
  b = 4        ← a * 2
  c = 6        ← a * 3
  d = 4 + 6    ← b(새) + c(새) = 10 ✅ (한 번만 계산)
```

Push-Pull 알고리즘은 Push 단계에서 `b`, `c`, `d` 모두를 dirty로 표시만 해두고, Pull 단계에서 위상 정렬 순서로 `b` → `c` → `d`를 계산합니다. `d`는 항상 `b`와 `c`가 모두 최신인 상태에서 계산되므로 Glitch가 발생하지 않습니다.

## effect()가 표준에 없는 이유

눈치채셨겠지만, 앞의 카운터 예제에서 사용한 `effect()`는 표준 제안에 포함되어 있지 않습니다. 의도적인 설계 결정입니다.

`effect()`는 "Signal이 바뀌면 부수효과를 실행하라"는 기능인데, 핵심 질문은 **언제** 실행하느냐입니다.

- 동기적으로 즉시? (Solid.js)
- 마이크로태스크로? (Vue)
- `requestAnimationFrame`에? (일부 UI 라이브러리)
- 배치해서 한꺼번에? (React 철학)

정답이 없습니다. 프레임워크마다 전략이 다르고, 이걸 표준에서 하나로 강제하면 오히려 프레임워크의 유연성을 해치게 됩니다.

대신 표준은 `Signal.subtle.Watcher`라는 **기반 도구**만 제공하고, 각 프레임워크가 자신의 스케줄링 전략에 맞게 `effect()`를 구현하도록 합니다.

### Watcher로 effect 구현하기

표준 폴리필 저장소에서 제공하는 `effect()` 구현 예제입니다.

```javascript
function effect(callback) {
  let cleanup;

  const computed = new Signal.Computed(() => {
    cleanup?.();                      // 이전 정리 함수 실행
    cleanup = callback();             // 콜백 실행, 정리 함수 저장
  });

  const watcher = new Signal.subtle.Watcher(() => {
    // dirty해지면 마이크로태스크로 스케줄링
    queueMicrotask(() => computed.get());
  });

  watcher.watch(computed);
  computed.get(); // 최초 실행 — 의존성 등록

  return () => {
    watcher.unwatch(computed);
    cleanup?.();
  };
}
```

동작 과정을 단계별로 보겠습니다.

```
1. effect(callback) 호출
   │
   ▼
2. Computed 생성 + watcher.watch(computed)
   │
   ▼
3. computed.get() — 최초 실행
   │  callback() 내부에서 signal.get() 호출
   │  → 자동으로 의존성 등록
   │
   ▼
4. 나중에 의존하는 Signal이 변경됨 (signal.set(...))
   │
   ▼
5. Push: computed가 Dirty로 표시
   │
   ▼
6. Watcher의 notify 콜백 호출
   │  → queueMicrotask(() => computed.get())
   │
   ▼
7. 마이크로태스크 실행 → computed.get()
   │  → Pull: callback() 재실행
   │  → 새로운 의존성 다시 등록
```

핵심은 `Watcher`가 변경을 감지하고, `Computed`가 실제 콜백 실행과 의존성 추적을 담당한다는 것입니다. 스케줄링 방식(`queueMicrotask`)은 프레임워크가 자유롭게 바꿀 수 있습니다.

## 그 외 API

### Signal.subtle.untrack()

의존성 추적을 일시적으로 중단합니다.

```javascript
const computed = new Signal.Computed(() => {
  const tracked = source.get();           // 의존성으로 등록됨
  const untracked = Signal.subtle.untrack(
    () => other.get()                     // 의존성으로 등록되지 않음
  );
  return tracked + untracked;
});
```

`other`가 바뀌어도 `computed`는 다시 계산되지 않습니다. 유용하지만 위험한 API입니다. 추적하지 않은 값이 결과에 영향을 준다면 의도하지 않은 stale 값을 보게 됩니다.

### 커스텀 동등성 비교

기본적으로 `Object.is()`로 값 변경을 판단합니다. 객체를 다루는 경우 커스텀 비교 함수를 제공할 수 있습니다.

```javascript
const user = new Signal.State(
  { name: "Alice", age: 30 },
  {
    equals: (prev, next) => prev.name === next.name && prev.age === next.age
  }
);

user.set({ name: "Alice", age: 30 }); // equals가 true → 변경 안 됨으로 판단
```

동등하다고 판단되면 dirty 플래그가 전파되지 않으므로, 불필요한 재계산을 방지할 수 있습니다.

### watched / unwatched 콜백

Signal이 감시 대상이 되거나 해제될 때 실행되는 콜백입니다. 외부 데이터 소스 연결에 유용합니다.

```javascript
const windowWidth = new Signal.State(window.innerWidth, {
  [Signal.subtle.watched]() {
    // 누군가 이 Signal을 쓰기 시작함 → 이벤트 리스너 등록
    window.addEventListener("resize", update);
  },
  [Signal.subtle.unwatched]() {
    // 아무도 안 씀 → 이벤트 리스너 해제
    window.removeEventListener("resize", update);
  }
});

function update() {
  windowWidth.set(window.innerWidth);
}
```

사용하는 곳이 없으면 이벤트 리스너를 자동으로 해제해서 메모리 누수를 방지합니다.

## 프레임워크와의 관계

이 제안의 목표는 기존 프레임워크를 대체하는 것이 아닙니다. 프레임워크 **아래**에 깔리는 공통 기반을 제공하는 것입니다.

```
현재:
┌──────────┐  ┌──────────┐  ┌──────────┐
│  Angular  │  │   Vue    │  │  Solid   │
│ Signals   │  │  Refs    │  │ Signals  │
│ (자체구현) │  │(자체구현) │  │(자체구현) │
└──────────┘  └──────────┘  └──────────┘
     ❌ 서로 호환 불가

목표:
┌──────────┐  ┌──────────┐  ┌──────────┐
│  Angular  │  │   Vue    │  │  Solid   │
│  (UI/DX)  │  │  (UI/DX) │  │  (UI/DX) │
└────┬─────┘  └────┬─────┘  └────┬─────┘
     │              │              │
     └──────────────┼──────────────┘
                    │
          ┌─────────┴─────────┐
          │  Standard Signals  │
          │   (TC39 표준)       │
          └───────────────────┘
     ✅ 반응형 로직 공유 가능
```

표준 Signal 위에서 만든 라이브러리는 Angular에서도, Vue에서도, Solid에서도 동작할 수 있습니다. 프레임워크는 UI 렌더링, 컴포넌트 모델, 스케줄링 같은 **자기만의 영역**에 집중하면 됩니다.
