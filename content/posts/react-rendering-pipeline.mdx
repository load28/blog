React의 렌더링을 "컴포넌트 함수를 다시 실행하는 것"이라고만 이해하면 몇 가지 질문에 답하기 어렵습니다. `useLayoutEffect`는 왜 DOM 측정이 가능한가, `useEffect`는 언제 실행되는가, 리렌더가 여러 번 DOM을 수정하는데 왜 화면이 깜빡이지 않는가. 이 글에서는 초기 마운트와 리렌더의 흐름을 단계별로 정리하면서, 내부에서 실제로 무슨 일이 일어나는지 살펴봅니다.

## 파이프라인 전체 구조

React는 컴포넌트 생명주기를 네 단계로 나눕니다.

```
Trigger → Render → Commit → Passive Effects
```

| 단계 | 역할 |
|---|---|
| Trigger | `setState`, props 변경 등으로 업데이트 시작 |
| Render | Fiber 트리를 순회하면서 변경사항 계산 |
| Commit | 실제 DOM 반영 + layout effect 실행 |
| Passive Effects | `useEffect` setup / cleanup 실행 |

Render는 중단·취소 가능한 비동기 작업이고, Commit은 동기적이며 취소할 수 없습니다. Passive Effects는 브라우저 페인트 이후 별도 태스크로 실행됩니다.

## Fiber가 "변경된 곳만" 찾아가는 방식

Commit 단계가 트리 전체를 매번 훑지 않고 필요한 곳만 건드릴 수 있는 이유는 각 Fiber 노드가 두 가지 비트 필드를 함께 갖기 때문입니다.

- **`flags`**: 이 노드가 할 일. `Placement`(새 DOM 부착), `Update`(속성·텍스트 변경), `Deletion`(삭제) 같은 값들이 비트 OR로 조합되어 들어갑니다.
- **`subtreeFlags`**: 자손 중 누군가 할 일이 있음을 알리는 요약 비트.

Render 단계에서 자식의 `flags`와 `subtreeFlags`가 부모의 `subtreeFlags`로 OR 집계되어 올라갑니다. Commit은 트리를 내려가면서 이 요약 비트만 확인하고, 비어 있으면 그 서브트리를 통째로 스킵합니다. 덕분에 변경이 없는 가지는 방문조차 하지 않습니다.

## 각 단계가 독립적인 DFS 순회다

Commit phase는 하나의 큰 덩어리가 아니라 여러 sub-phase로 나뉘고, **각 sub-phase가 Fiber 트리를 독립적으로 한 번씩 DFS 순회**합니다. 각 순회는 자기만의 관심 마스크를 가지고 움직입니다.

| Sub-phase | 관심 마스크 | 하는 일 |
|---|---|---|
| Mutation | `MutationMask` | DOM 조작 (`Placement`, `Update`, `Deletion`) + 이전 useLayoutEffect cleanup |
| Layout | `LayoutMask` | useLayoutEffect setup |
| Passive unmount | `PassiveMask` | useEffect cleanup |
| Passive mount | `PassiveMask` | useEffect setup |

한 번의 DFS 안에서 동작은 단순합니다.

```
  ↓ Top-down  : 부모 → 자식으로 내려가며 subtreeFlags 확인
                해당 마스크 비트가 0이면 서브트리 통째로 스킵
                (실제 작업은 하지 않음)

  ↑ Bottom-up : 자식 → 부모로 올라오며 본인 flags 확인
                해당 마스크 비트가 켜져 있으면 실제 작업 수행
```

"Commit은 bottom-up이다"라는 단순화가 부정확한 이유가 여기 있습니다. top-down으로 내려가긴 하는데 그건 가지치기용이고, 실제 작업은 올라올 때만 일어납니다.

그리고 sub-phase끼리는 **완전히 순차적**으로 실행됩니다. mutation 순회가 트리 전체를 다 끝낸 뒤에야 layout 순회가 트리 전체를 다시 돕니다. 중간에 섞이지 않습니다.

effect 훅에는 한 가지 추가 플래그가 있습니다. 각 effect는 deps 비교 결과에 따라 `HookHasEffect` 태그가 붙거나 빠지는데, cleanup과 setup은 **이 태그가 붙은 effect만 실행**합니다. deps가 같으면 순회는 해당 fiber를 지나가더라도 effect는 실행되지 않습니다.

## 초기 마운트: 메모리 조립 → 한 번에 부착

```
[Render phase — 비동기, 중단 가능]
  ↓ Top-down (beginWork): Parent 함수 실행 → Child 함수 실행
  ↑ Bottom-up (completeWork):
      · Child  : DOM 노드 생성(detached) → 부모 DOM에 조립
      · Parent : DOM 노드 생성(detached) → 자식 DOM 조립
      · 루트 fiber에 Placement 플래그 설정
      · subtreeFlags 상위 전파

[Mutation 순회 — DFS]
  ↓ Top-down : subtreeFlags & MutationMask 로 가지치기 (작업 없음)
  ↑ Bottom-up:
      · Placement 플래그가 켜진 fiber에서
        조립된 루트 DOM을 container에 한 번에 부착
        ★ 실제 화면에 영향을 주는 유일한 DOM 조작

[Layout 순회 — DFS]
  ↓ Top-down : subtreeFlags & LayoutMask 로 가지치기
  ↑ Bottom-up:
      · Child useLayoutEffect setup
      · Parent useLayoutEffect setup

[브라우저 페인트]

[Passive mount 순회 — DFS]
  ↓ Top-down : subtreeFlags & PassiveMask 로 가지치기
  ↑ Bottom-up:
      · Child useEffect setup
      · Parent useEffect setup
```

핵심은 Render 단계의 bottom-up에서 만들어지는 DOM이 **document와 분리된 상태**라는 점입니다. Render 전체가 화면에 아무 영향도 주지 않고, 실제 문서에 영향을 주는 호출은 Mutation 순회의 bottom-up에서 `Placement` 플래그를 만나 container에 붙이는 단 한 번뿐입니다. 자식 fiber들은 이미 부모 DOM 안에 조립되어 있으므로 루트 하나만 붙이면 서브트리 전체가 한 번에 문서에 들어갑니다.

## 리렌더: live DOM을 직접 수정

```
[Render phase]
  ↓ Top-down (beginWork): Parent 함수 실행 → Child 함수 실행
  ↑ Bottom-up (completeWork):
      · 변경된 fiber에 Update / Deletion 플래그 설정
      · deps가 바뀐 effect에만 HookHasEffect 태그 유지
      · subtreeFlags 상위 전파
      ★ 이 단계에선 DOM을 건드리지 않음

[Mutation 순회 — DFS 한 번]
  ↓ Top-down : subtreeFlags & MutationMask 로 가지치기 (작업 없음)
  ↑ Bottom-up: 한 fiber에서 올라올 때마다 아래를 이어서 실행
      · Child fiber 복귀:
         1) HookHasEffect가 붙은 useLayoutEffect cleanup
         2) Update 플래그가 있으면 해당 fiber의 DOM 직접 수정
      · Parent fiber 복귀:
         1) useLayoutEffect cleanup
         2) DOM 직접 수정
      ★ cleanup과 DOM 수정이 같은 순회 안에서 fiber 단위로 묶임

[Layout 순회 — 또 한 번의 DFS]
  ↓ Top-down : subtreeFlags & LayoutMask 로 가지치기
  ↑ Bottom-up:
      · Child useLayoutEffect setup (HookHasEffect인 것만)
      · Parent useLayoutEffect setup

[브라우저 페인트]

[Passive unmount 순회 — DFS]
  ↓ Top-down : subtreeFlags & PassiveMask 로 가지치기
  ↑ Bottom-up:
      · Child useEffect cleanup (HookHasEffect인 것만)
      · Parent useEffect cleanup

[Passive mount 순회 — DFS]
  ↓ Top-down : subtreeFlags & PassiveMask 로 가지치기
  ↑ Bottom-up:
      · Child useEffect setup
      · Parent useEffect setup
```

핵심 포인트가 두 가지입니다.

**첫째, cleanup과 DOM 수정이 같은 mutation 순회의 bottom-up 안에서 fiber별로 묶여 실행됩니다.** "자식 cleanup 전부 → 자식 DOM 수정 전부 → 부모 cleanup → 부모 DOM 수정"이 아니라, 한 fiber에서 올라올 때 그 fiber의 cleanup과 DOM 수정(`Update`·`Deletion` 플래그가 있다면)이 이어서 일어나고, 그 다음 부모로 올라가서 같은 일을 반복합니다.

**둘째, useLayoutEffect setup은 별개의 DFS 순회입니다.** mutation 순회의 top-down과 bottom-up이 트리 전체를 다 끝낸 뒤, layout 순회가 top-down 가지치기부터 새로 시작해서 bottom-up에서 setup을 실행합니다. 그래서 모든 DOM 수정이 끝난 뒤 setup이 실행되고, setup 내부에서 안전하게 변경된 DOM을 측정할 수 있습니다.

useEffect도 마찬가지입니다. passive unmount 순회와 passive mount 순회가 완전히 분리되어 있어, unmount의 bottom-up에서 cleanup 전체가 끝난 뒤 mount의 bottom-up에서 setup 전체가 실행됩니다.

## 초기 마운트 vs 리렌더의 DOM 조작

두 경우의 DOM 조작 방식은 근본적으로 다릅니다.

| 항목 | 초기 마운트 | 리렌더 |
|---|---|---|
| DOM 노드 생성 | Render 단계 | 필요 시 Commit 단계 |
| 조립 장소 | 분리된 메모리상 | 실제 문서 트리 |
| live DOM 조작 횟수 | 1번 | 변경 수만큼 여러 번 |

"React는 DOM 조작을 메모리에 모았다가 한 번에 적용한다"는 설명은 **초기 마운트에만 해당**됩니다. 리렌더에서는 실제 문서 트리를 직접 여러 번 수정합니다.

## 그런데 왜 깜빡이지 않는가

리렌더가 live DOM을 여러 번 수정하는데도 중간 상태가 보이지 않는 이유는 React의 배치 전략이 아닙니다. 브라우저와 JavaScript 엔진의 본질적 속성입니다.

**1. JS 실행 중에는 페인트할 수 없다**  
Commit phase 전체가 하나의 JS 태스크 안에서 실행됩니다. 중간 DOM 조작은 사용자 눈에 노출될 수 없습니다.

**2. 브라우저가 reflow를 자동 배치한다**  
DOM 변경이 여러 번 일어나도 브라우저는 즉시 reflow하지 않습니다. JS 태스크가 끝날 때까지 미뤘다가 한 번에 처리합니다.

**3. React가 쓰기와 측정을 별도 순회로 분리한다**  
mutation 순회는 DOM 쓰기만 하고, 그 다음 layout 순회에서 필요 시 측정을 합니다. 두 순회가 섞이지 않으므로 mutation 중간에 강제 reflow가 발생하지 않고 브라우저의 자동 배치가 온전히 작동합니다.

`useLayoutEffect` 안에서 `getBoundingClientRect`, `offsetHeight`, `getComputedStyle` 같은 측정 API를 부르면 강제 동기 reflow(layout thrashing)가 발생할 수 있습니다. React 내부는 이를 피하도록 설계되어 있지만 사용자 코드에서는 주의가 필요합니다.

## useLayoutEffect vs useEffect

| | `useLayoutEffect` | `useEffect` |
|---|---|---|
| 실행 시점 | Commit layout 단계 | Passive Effects phase |
| 동기 / 비동기 | 동기 | 비동기 |
| 페인트 블로킹 | O | X |
| DOM 측정 가능 | O (이미 변경됨) | O |
| 실행 방향 | 자식 → 부모 | 자식 → 부모 |

둘 다 실행 방향은 같습니다. 차이는 "페인트 전이냐, 페인트 후냐"입니다. `useLayoutEffect`가 "DOM 변경 전"에 실행된다는 건 흔한 오해이고, 실제로는 **DOM 변경 후, 페인트 전**입니다.

## 로그로 검증하기

```jsx
function Child({ text }) {
  useLayoutEffect(() => {
    console.log("Child layout setup");
    return () => console.log("Child layout cleanup");
  }, [text]);
  useEffect(() => {
    console.log("Child effect setup");
    return () => console.log("Child effect cleanup");
  }, [text]);
  return <p>{text}</p>;
}

function Parent() {
  const [n, setN] = useState(0);
  useLayoutEffect(() => {
    console.log("Parent layout setup");
    return () => console.log("Parent layout cleanup");
  });
  useEffect(() => {
    console.log("Parent effect setup");
    return () => console.log("Parent effect cleanup");
  });
  return (
    <div>
      <button onClick={() => setN(n + 1)}>{n}</button>
      <Child text={`count ${n}`} />
    </div>
  );
}
```

버튼 클릭 후 리렌더의 로그 순서입니다.

```
Child layout cleanup
Parent layout cleanup
Child layout setup
Parent layout setup
[브라우저 페인트]
Child effect cleanup
Parent effect cleanup
Child effect setup
Parent effect setup
```

cleanup 전체가 끝난 뒤 setup 전체가 실행되고, layout effect는 페인트 전, passive effect는 페인트 후에 실행됩니다.

## 자주 발생하는 오해

**"useLayoutEffect는 DOM 변경 전에 실행된다"**  
DOM 변경 후, 브라우저 페인트 전입니다. 기준점은 mutation이 아니라 paint입니다.

**"useEffect는 커밋 단계에서 실행된다"**  
등록만 커밋 단계에서 하고, 실제 콜백은 커밋 밖의 Passive Effects phase에서 실행됩니다.

**"React는 DOM 조작을 메모리에 모았다가 한 번에 적용한다"**  
초기 마운트에만 해당되고, 리렌더는 live DOM을 여러 번 직접 조작합니다.

**"cleanup은 리렌더에서만 실행된다"**  
운영 환경에서는 맞지만, 개발 환경의 StrictMode에서는 초기 마운트에도 mount → unmount → mount 사이클로 cleanup이 한 번 실행됩니다.

## 정리

React의 렌더링 파이프라인은 세 가지 포인트로 요약됩니다.

첫째, **Render는 오프스크린에서, Commit은 실제 화면에서** 일어납니다. Render 단계에서 일어나는 모든 작업은 화면에 영향을 주지 않습니다.

둘째, **초기 마운트와 리렌더의 DOM 조작 방식이 다릅니다.** 초기 마운트는 분리된 메모리에서 조립해 한 번에 붙이고, 리렌더는 live DOM을 직접 여러 번 수정합니다.

셋째, **리렌더에서 깜빡임이 없는 이유는 React가 아니라 JS 이벤트 루프와 브라우저의 reflow 배치 때문입니다.** React는 그 위에서 쓰기와 측정을 단계로 분리해 자동 배치를 극대화할 뿐입니다.

"React 렌더링"이라는 말은 가상 DOM 계산, 실제 DOM 수정, effect 실행을 뭉뚱그린 표현입니다. 각 단계가 언제 실행되고 어떤 순서로 흐르는지 분리해서 보면, `useLayoutEffect`를 언제 써야 하는지, `useEffect` 안에서 상태 업데이트를 하면 왜 추가 렌더가 트리거되는지, 최적화가 어디에서 의미 있는지 같은 질문에 일관된 답을 낼 수 있습니다.
